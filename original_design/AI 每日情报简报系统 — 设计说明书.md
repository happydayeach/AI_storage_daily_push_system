# AI 每日情报简报系统 — 设计说明书

> 版本：v1.0（讨论定稿，进入实现前的最终版）
> 目标：复刻并改进类似"欧洲存储与智能协作市场每日简报"的自动化情报产品：界面+主题、消息抓取、深度分析、多渠道推送，全程无人在环。

---

## 1. 核心需求（不可动摇的约束）

- **数据源不固定**：不维护RSS白名单，每轮实时检索
- **时间窗口**：只抓取过去 24–48 小时内发布的内容
- **去重**：每天与"昨天及近期"已发布的热点做去重，避免重复报道
- **语言策略**：优先英文数据源，减少中文转译/转发导致的旧闻重复
- **持续报道**：对同一热点事件保持跨天追踪，报道其"新进展"而非重复背景
- **多 Agent 拆分**：链路拆成职责单一的多个 Agent
- **无人在环**：所有判断（去重阈值、信源质量、异常处理）必须程序化，不依赖人工实时确认
- **可复用**：跑通一次后长期复用，后续只做增量改进，不重新设计

---

## 2. 部署与调度方案

**结论：不自建服务器，用 GitHub 生态完整替代。**

| 环节 | 方案 |
|---|---|
| 调度 | GitHub Actions 的 scheduled workflow（cron），每天定时触发 |
| 运行环境 | GitHub Actions runner（国际出口，直连英文信源和 Claude API，不需要用户本地VPN） |
| 状态持久化（去重库、历史归档） | 用仓库本身当数据库：story 库存为 SQLite/JSON 文件，pipeline 最后一步自动 `git commit` 回仓库；天然带版本记录、可审计 |
| 详情页托管 | GitHub Pages：每天生成的 HTML 发布到 `docs/` 目录，产出公开可访问的当日详情页 URL |
| 密钥管理 | 全部放 GitHub Actions Secrets（Claude API Key、新闻检索 API Key、pushplus token、企业微信/飞书 webhook） |

选择理由：免费额度足够"每天跑一次、十几分钟"的任务；不需要用户维护服务器和网络（VPN问题自动规避）；调度、存储、发布、密钥管理一站式解决，全部与"改进即 push 代码生效"的复用理念吻合。

## 3. 主题（Theme）设计

- **起步范围**：先做单一主题（如"欧洲存储市场"）
- **架构要求**：所有数据结构从一开始就以 `theme_id` 为一等公民建模，即使当前只有一个实例，后续加新主题只需新增一份配置文件，不改动代码/模板

`theme_config`（每个主题一份，yaml/json）包含：
- 关键词矩阵（多组同义/相关查询，覆盖不同子话题，而非单一大杂烩查询）
- 信源黑白名单及初始权重
- 分类体系（该主题下有哪几个大类，如"产业热点" / "垂直行业热点"）
- 深度分析模板结构（如"背景 / 技术分析 / 市场影响 / 竞对信号"四段）
- 视觉主题变量（色板、图标映射，见第7节）
- 推送目标列表（该主题绑定的 pushplus token / 企业微信 webhook / 飞书 webhook）

---

## 4. 整体数据流程

```
[主题配置 theme_config]
        ↓
Agent 1  信源发现            → 候选文章列表（24-48h窗口，英文）
        ↓
Agent 2  抓取与提炼           → 结构化事件卡片（转述摘要+实体抽取）
        ↓
Agent 3  去重聚类             → 打标签：new / update / duplicate（读取历史story库）
        ↓
Agent 4  深度分析             → 完整简报条目（仅处理 new / update）
        ↓
Agent 5  质检自检             → 通过则继续；异常则降级/跳过（不阻塞、不等人）
        ↓
Agent 6a 详情页生成           → HTML → GitHub Pages 发布 → 当日URL
Agent 6b 推送消息体生成       → 精简摘要 + URL → 三渠道各自适配格式
        ↓
Agent 7  推送                → pushplus / 企业微信 / 飞书
        ↓
写回 story 库 + git commit（供次日去重与持续报道使用）
```

---

## 5. 各 Agent 详细设计

### Agent 1：信源发现
- **输入**：theme_config 的关键词矩阵
- **做法**：对每个关键词分别用**带时间过滤的新闻检索接口**查询（不用普通网页搜索，因其不保证时间新鲜度）；候选方案包括 Bing News Search / NewsAPI / **GDELT**（免费全球新闻事件库，自带同事件多报道聚类信息，值得优先技术验证，可减轻 Agent 3 负担）
- **前置去重**：同URL去重；标题字符串相似度粗筛，合并明显转载（保留最早发布源）
- **输出**：`{url, title, snippet, published_at, domain}[]`，过滤掉超出24-48h窗口的

### Agent 2：抓取与提炼
- **输入**：Agent 1 候选列表
- **做法**：逐条抓正文，LLM 做**转述式摘要**（严禁逐句引用原文，遵守版权）；抽取结构化字段
- **输出**：
```json
{
  "event_type": "财报/漏洞/产品发布/监管/合作...",
  "entities": ["公司", "产品", "法规"],
  "key_numbers": ["金额", "日期", "编号"],
  "summary_zh": "转述摘要",
  "source_url": "...",
  "published_at": "...",
  "domain": "..."
}
```
- **副产出**：为每个 domain 累计入选次数 → 信源质量分（一手信源权重逐渐升高，聚合转载站权重下降）——这是"无人在环下自我改进"的具体机制

### Agent 3：去重聚类（核心难点）
- **输入**：Agent 2 的事件卡片 + 历史 story 库（近 7–14 天，含 embedding）
- **做法**：
  1. 对每条摘要生成 embedding
  2. 与 story 库做 cosine similarity
  3. 双阈值判定（具体数值待实现阶段用真实样本校准）：
     - **≥ 阈值A（如0.88+）**：判定重复报道 → 丢弃
     - **阈值B ~ 阈值A（如0.75~0.88）**：判定"同一事件最新进展" → 标记 `update`
     - **< 阈值B**：判定全新事件 → 标记 `new`
  4. 同批次内部也做一次同样比对（当天候选之间去重）
- **输出**：`{new: [...], update: [{story_id, 新增内容, 历史摘要}], duplicate_dropped_count}`

### Agent 4：深度分析
- **处理对象**：仅 `new` 和 `update` 标记的事件
- **版权原则**：严格转述改写，不拼接原文句子；引用来源用"XX报道"标注+链接，不摘录超过一句原文
- **信息增量**：对该事件做**二次定向检索**（用更具体的关键词，如已知实体+事件类型），合并多信源转述，避免空对空扩写
- **update 类型**：只生成"较上次的新进展"这一段，附带指回历史摘要，不重复讲背景 → 实现"持续报道"

### Agent 5：质检自检
- 程序化规则示例：条目总数是否在合理区间；摘要是否非空；来源链接是否齐全；关键环节是否有API报错/超时
- **失败即降级，不阻塞**：单条数据缺失只跳过该条；检索环节整体挂了则发送最简"今日检索异常，明日恢复"通知；所有异常写日志供事后查看，不需要实时人工介入

### Agent 6a：详情页生成
- 结构化数据（Agent 4 输出）套入固定 HTML 模板 → 完整详情页 → commit 到 `docs/` → GitHub Pages 发布 → 得到当日 URL

### Agent 6b：推送消息体生成
- 精简摘要文本 + 6a 产出的 URL，分别适配三种目标格式：
  - pushplus：较长文本/简单HTML片段
  - 企业微信 / 飞书：markdown 卡片（字数受限，webhook 格式不同，飞书还需处理签名校验）

### Agent 7：推送
- 统一推送适配器接口：`send(theme_id, title, content) -> 各渠道自行转换格式`
- 单渠道失败只记录日志+跳过，不影响其他渠道推送成功

## 6. 视觉主题系统（三层分离，长期复用）

| 层级 | 内容 | 更新频率 |
|---|---|---|
| **通用层**（代码，所有主题共用） | HTML骨架（头部→执行摘要区→分类导航→逐条展开区→页脚）；可复用组件（摘要卡片、锚点导航条、展开/收起交互、分类小节容器）；CSS变量框架的结构性部分（暗色模式适配、字号阶梯、间距系统）；移动端优先响应式规则 | 一次性做好，之后基本不改 |
| **主题可变层**（配置，每主题一份） | 色板（主色/辅助色/强调色）；图标映射表（`event_type → emoji`）；文案模板（标题、署名）；分类体系 | 新增主题时才新增一份 |
| **内容数据层**（每天动态生成） | Agent 4 输出的结构化 JSON，纯数据不含样式 | 每天自动生成 |

设计原则：模板不由 LLM 每天现场"设计"，避免风格漂移和浪费 token；日常运行时 Agent 6a 只是"把数据填进已定稿的模板"。

## 7. 数据模型草案

**theme_config**（配置文件）
```
theme_id, keywords[], source_whitelist/blacklist+weight,
categories[], analysis_template_sections[],
theme_colors, icon_map{event_type: emoji},
push_targets[{channel, token/webhook}]
```

**story库**（按 theme_id 分区，跨天持久化）
```
story_id, theme_id, first_seen_date, last_updated_date,
summary_history[]（每次更新追加，不覆盖）,
embedding, source_urls[]
```

**push_log**
```
theme_id, date, channel, content_sent, status, timestamp
```

---

## 8. 版权合规原则（贯穿 Agent 2 / 4）

- 全篇转述改写，不逐字复制原文
- 单条引用不超过一句，且需明确标注来源+链接
- 摘要/深度分析都必须是"用自己的话重新组织"，不是"去掉引号的原文"

---

## 9. 已确认的关键决策汇总

| 决策项 | 结论 |
|---|---|
| 运行环境 | GitHub Actions（无需自建服务器/VPN） |
| 详情页托管 | GitHub Pages |
| 状态存储 | 仓库内文件（SQLite/JSON）+ git commit 归档 |
| 主题范围 | 先单主题，架构预留多主题扩展（`theme_id`建模） |
| 推送渠道 | pushplus + 企业微信/飞书（统一适配器接口） |
| 去重方式 | embedding 语义相似度双阈值（具体数值待实现阶段校准） |
| 模板设计 | 通用层/主题层/数据层三层分离 |

## 10. 待实现阶段确定的参数（不阻塞设计，标注待办）

- 去重相似度阈值 A / B 的具体数值（需真实样本调参）
- 新闻检索接口最终选型（GDELT vs NewsAPI vs Bing News，需测试可用性与配额）
- embedding 模型选型（是否用本地模型以减少额外API依赖）

---

## 11. 建议实施顺序

1. **模板与视觉验收**（当前阶段）：通用HTML模板 + 存储主题配置 + 假数据 → 出可视化效果，定稿视觉风格
2. **Agent 1+2+3 打通**（检索→提炼→去重）：先人工观察几天结果，校准相似度阈值，确认去重效果符合预期
3. **接入 Agent 4（深度分析）+ Agent 6/7（渲染+推送）**：全链路打通
4. **观察运行稳定性**，视需要加质检规则、调整信源权重
5. **（可选）扩展第二个主题**，验证多主题架构预留是否真的"零改动"生效
